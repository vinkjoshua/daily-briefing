# Daily Briefing v1.1: simpler setup and tuning

Approved in conversation on 2026-10-06. This supersedes the unapproved proposal on `docs/v1.1-onboarding-plan`.

## Outcome

With uv and Git, a user can complete guided setup, create a private personal GitHub repository, and optionally start their first cloud briefing. Later they can edit, validate, generate a local preview, review, and explicitly publish. Support macOS, Linux, and WSL on x86-64 and ARM64. Native Windows is excluded.

## Accepted decisions

- Narrow v1.1 to setup, deterministic personalization, local preview, and explicit publishing.
- Reuse GitHub CLI; automatically download a pinned copy when necessary.
- Save answers directly as Markdown and copy selected existing section presets. No AI drafting loop.
- Offer the first cloud launch after reviewing setup; local preview is optional.
- Preserve existing cloud device-login reconnect, encryption format, secret names, and v1 instances.
- Use subagents and TDD. Merging, releases, moving v1, updating the public template and personal instance require separate approval.

## Commands and behavior

- `init [directory]`: default destination/repository `my-briefing`; guide GitHub login, SMTP, interests, sections, IANA timezone, and daily start time (default 07:00). Test email before remote creation. Show the account/repository/recipient/schedule/sections and confirm publication. Upload SMTP_USER, SMTP_PASSWORD and a generated BRIEFING_KEY before a runnable workflow is pushed. Offer first launch; cloud workflow emails the ChatGPT device code. Display observed status and Actions URL, never claim that submission is completion.
- `./briefing try [--section <slug>] [--open]`: use local Codex credentials, generate preview.html in isolation, no email/publication/state updates. Guide local login if missing. No transfer of local credentials to the repository.
- `./briefing publish [--run]`: validate, review all outgoing commits and working changes, confirm, commit and push; optionally dispatch. Do not force push. Stop on conflicts with work preserved.
- Keep existing validate and Markdown-to-HTML preview commands compatible.

## Constraints

- Pin official Codex 0.160.0 and gh 2.102.0 distributions, preserving companion files. Verify embedded SHA-256 digests, extract safely, install atomically into a versioned application cache. Reuse matching installed versions.
- Use gh for authentication, repository/secrets/workflow operations and subprocess-scoped Git credential helpers. Let gh manage its own login storage. Never place secrets in command arguments, logs, remote URLs or tracked files.
- Bundle canonical starter resources with the installed CLI; launcher pins its released CLI version and cloud workflow retains @v1.
- Generalize the existing five section types; no Amsterdam/AI assumptions. Initial files are deterministic Markdown from answers and selected presets.
- Keep accepted setup work and minimal non-secret progress under Git metadata. Resume only that setup's repository; inspect remote state after uncertain responses. Never rotate an active instance's key or blindly redispatch.
- Generate native timezone-aware GitHub schedules, with retries +1h/+2h unless they cross local midnight. Keep existing daily guard and manual force behavior. Scheduling changes after setup are reviewed file edits, not a new command.
- Reuse prompt/sections/Codex/renderer for try. Temporary workspace contains only copies of interests, sections and state, rejects symlinks, discards generated state, outputs only HTML. Ignore user/project agent instructions and unrelated user config/rules while respecting the local auth store. Explicitly set live or disabled web search. Preserve sandbox and filtered environment.
- Read literal timezone/model/effort settings from workflow using existing PyYAML promoted to runtime. Reject unsupported expressions clearly. Generate new YAML from starter; do not introduce a general YAML editor.
- Publish only reviewed interests, sections, Markdown state, workflow, launcher and documentation. Exclude previews, archives, ciphertext and credentials. Use standard Git fetch/rebase/push for nonconflicting bot updates; preserve local work on conflict.
- Engine changes remain limited to onboarding needs: explicit web-search configuration, agent-instruction isolation and accurate device-login diagnostics. Keep existing renderer and encryption design.

## Validation and delivery

TDD for behavior; fake external services and real temporary Git repositories for integration. Check downloads/caching/platforms/space-containing paths, auth failures, collisions, SMTP rejection, cancellation and resumption, cloud login/reconnect, preview immutability, publication history/path restrictions, bot updates/conflicts and schedules. Run pytest, Ruff check and format checks, actionlint and installed-wheel tests. Prepare Linux/macOS CI and WSL smoke instructions. Live acceptance uses a throwaway private repository pinned to candidate code, interactive credentials, and one scheduled run; report unavailable environments honestly.

## Deferred

Catalog commands, doctor, managed upgrades, laptop credential rotation, email-repair commands, AI onboarding drafts, custom OAuth infrastructure, and a general recovery framework.
