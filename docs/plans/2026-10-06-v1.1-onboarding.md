## 1. Outcome and agreed defaults

A user with **uv and Git** can run one command, complete guided authentication and personalization, and receive their first cloud-generated briefing:

```sh
uvx --from git+https://github.com/vinkjoshua/daily-briefing@v1 daily-briefing init
```

The resulting repository includes a `./briefing` launcher, so later commands require neither a global installation nor `gh`.

Agreed scope:

- Support macOS, Linux, and WSL on Intel/AMD and ARM where official binaries exist. Native Windows is outside v1.1.
- Download the pinned Codex distribution into an application cache; do not require Node or change globally installed tools.
- Target personal GitHub accounts and private repositories.
- Reuse the user's existing local Codex login for previews. Guide them through a separate laptop login if none exists.
- Require explicit publication after tuning, with a reviewed diff and confirmation.
- Preserve the normal repair experience: reconnect email → Run workflow → approve code.
- Keep SMTP delivery, the existing encryption format, and existing v1 instance compatibility.
- Require approval before merging, publishing the release, moving `v1`, or updating the public template.

## 2. User experience and command interfaces

### Guided setup

The wizard presents progress, preserves completed non-secret work, and gives an exact recovery command when interrupted.

1. **Check the machine.**
   Check uv, Git, supported platform, writable destination, and network access. Fetch Codex 0.160.0 from the official release into a versioned cache, preserving required companion files. Verify against shipped SHA-256 values before extraction and installation. Use atomic installation so interrupted downloads cannot leave a broken cached executable. Official release distributions and checksums are available. [Codex release assets](https://github.com/openai/codex/releases/expanded_assets/rust-v0.160.0)

2. **Connect GitHub.**
   Reuse a suitable `gh` token when available; otherwise use the project's OAuth device flow. Resolve and display the authenticated account, check permissions, and ask for the repository name, defaulting to `my-briefing`. Detect name collisions before further setup.

3. **Connect email.**
   Ask for provider and email address, with Gmail, iCloud, Fastmail, and custom SMTP options. Offer a different recipient as an optional setting. Provide the relevant App Password instructions, collect credentials through hidden input, and send a test email. Normalize Gmail's displayed password spaces only. Authentication or delivery errors return to this step without losing other answers.

4. **Connect ChatGPT.**
   Explain the device-login setting and authenticate using a fresh temporary `CODEX_HOME` with file-backed credentials. Open the browser and display the code immediately. Offer browser login when device login is unavailable; explain that cloud repair will require device login or laptop reconnect. Probe the login before continuing.

5. **Personalize and review.**
   Ask for home city, detected-and-confirmed IANA timezone, daily start time, professional interests, personal interests, and sections. Use `07:00` as the start-time default and explain that research and delivery happen afterwards.

   Codex drafts only the profile and selected section files in a temporary workspace, with web search explicitly disabled, medium effort, and a ten-minute timeout. Present the resulting profile and section summaries with **Keep**, **Redo with feedback**, and **Use plain presets**. Validate required files, section structure, selected-section coverage, and allowed output paths. The user review catches semantic mistakes; automated validation must not claim to establish factual correctness.

6. **Go live.**
   Show the repository, recipient, timezone, schedule, and selected sections for final confirmation. Create an empty private repository and populate it from starter files bundled with this CLI version. Upload all three secrets before pushing the first runnable workflow. Encrypt the latest login state after drafting, commit, push, and dispatch the first briefing.

   Display the actual run link and observed status. Distinguish **submitted**, **running**, and **completed**; do not promise an unverified fifteen-minute delivery time. Finish with the local folder, tuning commands, Actions notification settings link, and appropriate GitHub revocation instructions.

Creating an empty repository from packaged starter files replaces the template-generation API. The public template remains the manual browser fallback; setup no longer depends on its publication timing.

### Commands after setup

| Command | Behavior |
|---|---|
| `./briefing validate` | Validate the profile, sections, and supported workflow settings. |
| `./briefing catalog` | List generic presets and their summaries. |
| `./briefing catalog add <name>` | Add a preset with an ordered filename; preserve existing sections. |
| `./briefing try [--section <slug>] [--open]` | Generate `preview.html` using local Codex authentication; send no email. |
| `./briefing schedule --at HH:MM [--timezone IANA]` | Edit the local schedule consistently; publish separately. |
| `./briefing publish [--run]` | Validate, show the outgoing diff, confirm, authenticate, commit, and push. Optionally dispatch a normal run. |
| `./briefing reconnect [--repo owner/name]` | Replace cloud login credentials safely and verify them in Actions. |
| `./briefing reconnect --email` | Test replacement SMTP credentials and update email configuration without rotating Codex credentials. |
| `./briefing doctor` | Report local prerequisites, instance configuration, workflow state, secret-name presence, and recent run results. Never claim to inspect secret values. |
| `./briefing upgrade` | Prepare reviewed updates to managed instance files while preserving personalization and state; publish separately. |

Keep existing engine commands and the Markdown-to-HTML `preview` command compatible. Provide the equivalent full `uvx` invocation for reconnecting from a laptop without a local clone.

Agent instructions teach the complete loop: **edit → validate → preview → review → publish**. They also cover adding sections, exclusions, scheduling, watchlist changes, and troubleshooting. `CLAUDE.md` points to the shared instructions.

## 3. Implementation and recovery contracts

### GitHub and publication

- Implement a small REST client using `urllib`, with injectable transport, clock, and browser opener. Handle device-flow polling, denial, expiry, rate limits, timeouts, insufficient permissions, and restricted Actions settings.
- Register a project-owned OAuth app with device flow enabled before live verification. Embed only its public client ID. Request `repo` and `workflow`; never borrow another application's client ID. [GitHub device flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow)
- Keep GitHub tokens in memory. Supply Git authorization through subprocess-scoped configuration, with clean remote URLs and redacted diagnostics. Do not write credentials into Git config or command arguments.
- Use repo-local identity derived from the authenticated account. Revocation guidance must distinguish the project OAuth grant from an existing GitHub CLI grant.
- Package starter files from the canonical template source during the build; test the installed wheel's resources.
- Add a small instance marker identifying the format version and repository. Resume only an instance created by this setup or a positively identified legacy briefing repository. Reject unrelated repositories and directories.
- Publishing includes only reviewed configuration, section, documentation, launcher, and user-edited Markdown state changes. It excludes credentials, runtime archives, and generated previews.
- Fetch remote changes before publishing. Handle nonconflicting bot updates, but stop on conflicts, unsupported local history, or unexpected workflow structure. Preserve local work and never force-push.

### Interrupted setup and reconnect

Maintain an atomic, non-secret operation journal under the local Git metadata. Record repository identity, phase, relevant commit IDs, and previous workflow state. Never journal passwords, encryption keys, or plaintext authentication.

**New setup:**

- Perform authentication, email testing, and personalization before creating the remote repository.
- Upload secrets before publishing the runnable workflow.
- After an uncertain push or dispatch response, inspect remote state before retrying.
- On restart, preserve accepted personalization. Re-request secrets or login only when required.
- A completed installation routes to tuning or reconnect; rerunning `init` must not reset it.

**Laptop reconnect:**

1. Authenticate GitHub and obtain a fresh, separately probed cloud login.
2. Acquire a local operation lock, record the existing workflow state, and disable new workflow triggers.
3. Wait for all existing nonterminal runs to finish. Show progress; a bounded timeout aborts before credential changes and restores the prior workflow state.
4. Fetch the latest repository state, generate a new key, encrypt the fresh login, and verify local decryption.
5. Push the replacement ciphertext, then update `BRIEFING_KEY`.
6. Re-enable the workflow and dispatch a login-only verification run.
7. Report success only when verification and credential persistence succeed. Restore an originally disabled workflow to its previous state afterwards.

If interrupted after changing only one side of the ciphertext/key pair, leave the workflow paused and resume by completing a fresh pair. Do not attempt to recover the old secret through GitHub: the API does not reveal secret values. [GitHub secrets API](https://docs.github.com/en/rest/actions/secrets#get-a-repository-secret)

Support one laptop maintenance operation per instance at a time. Cloud jobs remain serialized by the existing workflow concurrency group.

Add a backward-compatible `check-login` action input and workflow-dispatch input. This mode bypasses the daily sent guard, probes and persists authentication, and generates neither a device code nor a briefing. Reconnect adds the required wiring to recognized legacy workflows without replacing their schedule or content.

### Runtime, scheduling, and isolation

- Replace the Boolean device-login result with a typed result: `ok`, `expired`, `unavailable`, or `failed`, plus a sanitized diagnostic reason. Missing output alone must not diagnose a disabled toggle.
- Keep scheduled reconnect notices and manual device-code repair. Print codes live with unbuffered output.
- Explicitly disable web search for probes and personalization. Pass `project_doc_max_bytes=0` for unattended generation and previews, verified against the pinned CLI.
- Generate in disposable workspaces containing the necessary profile, sections, and copied state. Daily runs transfer resulting state back only after successful delivery; previews discard it.
- Preview may refresh the user's local Codex authentication, but must leave real briefing inputs, state, archives, and encrypted cloud credentials untouched.
- Use native IANA timezone scheduling. Generate the chosen start time and retries one and two hours later, omitting retries that cross local midnight. Keep the daily sent guard and add optional `not-before`, applied only to scheduled runs. Manual runs retain existing `force` behavior. [GitHub scheduling syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule)
- Use comment-preserving YAML edits; retain unrelated settings and reject ambiguous custom workflows.
- Add footer links for editing interests, browsing sections, and opening the workflow, resolving the actual default branch.
- Explain that SMTP failure notifications depend on GitHub notification preferences and that scheduling is approximate.

### Catalog, compatibility, and dependencies

- Provide research, open-source, events and talks, this week, book ahead, news digest, and new releases presets.
- Remove inherited Amsterdam and AI assumptions from generic presets and deterministic fallback content.
- Keep optional `summary` metadata compatible with section parsing; enforce matching template/catalog content.
- Add PyNaCl for GitHub secret encryption, comment-preserving YAML support, and portable timezone detection/data dependencies.
- Preserve the existing encrypted-login format and three secret names.
- Upgrade managed files through reviewed changes. Never overwrite interests, custom sections, archives, or authentication.
- Keep the private-word test active across new public resources and fixtures.

## 4. TDD tasks and subagent workflow

At implementation start, save the design and detailed task checklist under `~/projects/daily-briefing-notes/superpowers/`, then create a feature branch from the clean engine checkout.

For every behavioral change: **write a failing test → run it and observe the intended failure → implement the minimum change → pass the focused tests → refactor**. Record test evidence in each task handoff.

| Task | Deliverable | Depends on |
|---|---|---|
| 1 | Runtime login outcomes, login-only verification, isolation, explicit search settings, notices, footer | — |
| 2 | Packaged starter resources, platform preflight, verified Codex cache, launcher, generic catalog | — |
| 3 | GitHub device flow, REST operations, safe Git transport, instance recognition | — |
| 4 | Profile questions, drafting/review/fallback, workflow editing, scheduling | 1, 2 |
| 5 | Operation journal, resumable init, reconnect and email repair | 1–4 |
| 6 | Preview, reviewed publication, doctor, instance upgrade | 1–4 |
| 7 | Full integration scenarios, documentation, platform CI, release preparation | 5, 6 |

Delegation rules:

- Use isolated worktrees and narrowly assigned modules/tests.
- Run at most two implementation subagents concurrently, reserving a slot for an independent reviewer.
- Keep shared CLI integration, dependency changes, and final merges under the coordinating agent.
- Review every task for specification compliance, test quality, regression risk, and credential handling.
- Resolve findings before accepting the task.
- Finish with an independent whole-branch review and required CI checks.

## 5. Verification and release gates

**Automated acceptance coverage**

- Clean-machine bootstrap, cached reuse, corrupt downloads, unsupported platforms, paths with spaces, and cancellation.
- GitHub device-flow states, missing scopes, repository collisions, API failures, and credential redaction.
- Personalization success, malformed output, unexpected files, timeout, redo, and deterministic fallback.
- Interrupted setup at every remote mutation boundary; rerunning completed setup preserves customization.
- Reconnect interrupted before and after ciphertext push, secret update, workflow enablement, and verification dispatch.
- Active cloud runs are drained before rotation; failures never report a successful reconnect.
- Preview leaves the real repository unchanged except for the requested HTML output.
- Publish includes only reviewed changes, handles concurrent bot updates, and preserves work on conflicts.
- Scheduling covers Amsterdam and US DST transitions, non-DST and fractional-offset zones, late-night schedules, manual runs, and daily deduplication.
- Legacy v1 instances continue running and can receive reviewed upgrades.
- An end-to-end harness uses fake GitHub, a local bare Git remote, fake Codex, and fake SMTP. It decrypts the pushed auth blob using the uploaded key and asserts workflow contents, secret names, dispatches, and recovery behavior.

Run pytest, Ruff checks and formatting checks, actionlint, and installed-package tests. Run CI on Linux and macOS, with supported Python versions; verify WSL through a local smoke test.

**Live acceptance**

Use a throwaway private repository with both the CLI and workflow explicitly pointing to the candidate engine commit. Exercise:

- Setup without `gh`, global Codex, or existing Git credentials.
- Both authentication flows, test email, personalized files, and first briefing.
- The live AGENTS-ignore check against Codex 0.160.0.
- Preview, section tuning, and publication.
- Device-code repair after deleting the encrypted login, dispatched with `force: true` so the daily guard cannot hide the test.
- Laptop reconnect and login-only verification.
- Email credential replacement and an upgrade from a v1 instance.
- At least one scheduled cloud run.

Register and configure the OAuth app before these live checks. Human login approvals and App Password entry remain interactive; no credentials enter source control or test logs.

**Release**

Prepare version 1.1.0, changelog, command documentation, security/lifecycle documentation, and the manual browser fallback. After approval, merge, tag `v1.1.0`, move `v1`, publish the matching template, and apply reviewed managed-file updates to the personal instance.

Disable the old Windows scheduled task only after the replacement scheduled cloud run is verified. Retain the old local briefing folder as a fallback until that verification is complete.
